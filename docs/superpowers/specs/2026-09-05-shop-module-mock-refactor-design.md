# Shop Module Mock Refactor Design

วันที่: 5 กันยายน 2569 (2026-09-05)

> สถานะ: superseded เฉพาะข้อกำหนด mock-only โดย D23 ใน `docs/10_team_decisions.md` เอกสารนี้เก็บเป็นประวัติการออกแบบและใช้อ้างอิง domain/UI ได้ แต่ runtime ปัจจุบันต้องใช้ Supabase database repository และ mock ใช้เฉพาะ tests/offline demo

## 1. เป้าหมาย

ปรับส่วนงานของช้อปให้ตรงกับข้อตกลงล่าสุดใน `docs` โดยครอบคลุมการจัดการแผนก แพทย์ ตารางตรวจ และความจุรอบ ข้อมูลทั้งหมดในระยะนี้เป็น mock data และไม่เชื่อม Supabase

งานนี้ต้องทำให้ UI และกฎธุรกิจแยกจากแหล่งข้อมูล เพื่อให้เปลี่ยน mock repository เป็น Supabase implementation ได้ภายหลังโดยไม่ต้องรื้อหน้าจอหรือ validation หลัก

## 2. ขอบเขต

### หน้าแผนกและแพทย์

- แบ่งเป็นแท็บแผนกและแพทย์
- ค้นหาแผนก และเพิ่ม แก้ไข ลบหรือปิดใช้งาน
- ค้นหาแพทย์ กรองตามแผนก และเพิ่มหรือแก้ไขข้อมูลแพทย์กับความเชี่ยวชาญ
- ซ่อนรายการปิดใช้งานเป็นค่าเริ่มต้น และเปิดดูย้อนหลังด้วยตัวกรอง
- ก่อนลบหรือปิดใช้งานต้องแสดงหน้าต่างยืนยันและอธิบายผลกระทบ
- รายการที่มีประวัติอ้างอิงต้องปิดใช้งานแทนการลบจริง

### หน้าปฏิทินตารางตรวจ

- ใช้มุมมองรายสัปดาห์เป็นค่าเริ่มต้น
- เปลี่ยนสัปดาห์และกลับมายังสัปดาห์ปัจจุบันได้
- กรองตามแผนก แพทย์ และสถานะรอบ
- สร้าง ดู แก้ไข และปิดรอบตรวจ
- แสดงวัน เวลา แพทย์ แผนก จำนวนจอง ความจุ และสถานะ
- แยกสีสถานะ `available`, `full` และ `closed`
- Desktop แสดงปฏิทินรายสัปดาห์ ส่วนหน้าจอมือถือแสดงรายการเรียงตามวันและเวลา
- ไม่มี drag-and-drop

## 3. สิ่งที่ไม่อยู่ในขอบเขต

- Supabase migration, RLS, RPC และการอ่านเขียนฐานข้อมูลจริง
- การจองพร้อมกันแบบ atomic และ flow นัดหมายของปาย
- การเลื่อนนัดและกฎความจุเดิมระหว่างรอคำตอบข้อเสนอ
- หลายสาขา หลายเขตเวลา รอบข้ามวัน และตารางวันหยุดภายนอก
- การเก็บการแก้ไขหลัง refresh; mock data จะกลับเป็นค่าเริ่มต้น

## 4. สถาปัตยกรรม

แบ่งระบบเป็นสี่ชั้น:

1. **Domain types** — นิยาม `Department`, `Doctor`, `ScheduleSlot` และชนิดข้อมูลสำหรับสร้างหรือแก้ไข โดยไม่ผูกกับ React หรือ Supabase
2. **Mock catalog** — ข้อมูลตั้งต้น 4 แผนก แพทย์ 6 คน และรอบตรวจตาม Catalog กลาง ใช้รหัสคงที่เพื่อให้ทดสอบซ้ำได้
3. **Domain rules และ repository contract** — validation บริสุทธิ์และ interface สำหรับ query/command ของแต่ละ entity
4. **UI state และ pages** — provider ฝั่ง client ถือสถานะจำลอง เรียก repository และแสดงผลในสองหน้าหลัก

หน้า UI ต้องไม่แก้ array ของ mock data โดยตรง ทุกการเปลี่ยนแปลงผ่าน repository เพื่อให้เปลี่ยน implementation ภายหลังได้

## 5. แบบข้อมูล

### Department

- `id`
- `name`
- `description`
- `isActive`
- `hasHistory`

### Doctor

- `id`
- `fullName`
- `specialty`
- `departmentId`
- `isActive`
- `hasHistory`

### ScheduleSlot

- `id`
- `doctorId`
- `date` ในรูป `YYYY-MM-DD`
- `startTime` และ `endTime` ในรูป `HH:mm`
- `capacity`
- `bookedCount`
- `status` เป็น `available`, `full` หรือ `closed`
- `hasHistory`

`full` เป็นสถานะที่ repository คำนวณเมื่อ `bookedCount >= capacity` เว้นแต่รอบถูกปิด ซึ่งต้องคงเป็น `closed`

## 6. กฎธุรกิจ

- ใช้เขตเวลา `Asia/Bangkok` ทั้งระบบ
- ตารางปกติอยู่วันจันทร์ถึงศุกร์ เวลา 08:30–16:30 น. และไม่อนุญาตช่วงพัก 12:00–13:00 น.
- ไม่สร้างรอบข้ามวัน
- เวลาเริ่มต้องน้อยกว่าเวลาสิ้นสุด
- รอบของแพทย์คนเดียวกันในวันเดียวกันห้ามทับซ้อน โดยช่วงที่รอบหนึ่งสิ้นสุดตรงกับเวลาเริ่มของอีกรอบไม่ถือว่าทับ
- ความจุต้องเป็นจำนวนเต็มบวก และห้ามต่ำกว่าจำนวนที่จองแล้ว
- จำนวนจองต้องไม่ติดลบและไม่เกินความจุ
- แพทย์ต้องสังกัดแผนกที่เปิดใช้งานก่อนสร้างรอบใหม่
- รอบของแพทย์หรือแผนกที่ปิดใช้งานยังแสดงในประวัติ แต่สร้างรอบใหม่ไม่ได้
- entity ที่ `hasHistory` เป็นจริงใช้ soft delete; entity ที่ไม่มีประวัติสามารถลบออกจาก mock store ได้
- การปิดรอบไม่ลบประวัตินัดหรือเปลี่ยน `bookedCount`

หากกฎใดขัดกับเรื่องค้างใน `docs/10_team_decisions.md` จะไม่เพิ่มพฤติกรรมเกินข้อสรุปที่มีอยู่

## 7. Mock data

ใช้ข้อมูล Catalog ล่าสุด:

- 4 แผนก: เวชปฏิบัติทั่วไป, สุขภาพจิตและให้คำปรึกษา, วัคซีนและสร้างเสริมภูมิคุ้มกัน และกายภาพบำบัด
- แพทย์ 6 คน: Stephen Strange, Meredith Grey, Charles Xavier, Leonard McCoy, Bruce Banner และ Shuri Udaku
- ตารางตรวจสร้างจากรูปแบบรายสัปดาห์ใน Catalog โดยผูกวันที่ให้สัมพันธ์กับสัปดาห์ปัจจุบันใน `Asia/Bangkok`
- มี fixture สำหรับสถานะว่าง เต็ม ปิด และกรณีมีประวัติอ้างอิง

## 8. Data flow

1. Provider สร้าง repository จาก mock catalog หนึ่งครั้งเมื่อโหลดส่วน clinic
2. Page ขอ snapshot ผ่าน query ของ repository
3. ผู้ใช้ส่ง form; UI แปลงค่าพื้นฐานและส่ง command
4. Repository เรียก domain validation ก่อนแก้ state
5. เมื่อสำเร็จ provider เผยแพร่ snapshot ใหม่ให้ทั้งสองหน้า
6. เมื่อไม่สำเร็จ UI แสดงข้อความระดับ field หรือข้อความรวม โดยไม่เปลี่ยนข้อมูลเดิม

Repository จะคืนผลลัพธ์แบบ discriminated union เพื่อแยก success กับ validation error อย่างชัดเจน ไม่ใช้ exception สำหรับความผิดพลาดจากข้อมูลผู้ใช้

## 9. การจัดการสถานะ UI

- Loading แสดง skeleton หรือข้อความกำลังโหลดเมื่อ repository เริ่มต้น
- Empty แสดงคำอธิบายและปุ่มสร้างรายการที่สัมพันธ์กับตัวกรองปัจจุบัน
- Error แสดงข้อความที่เข้าใจได้และปุ่มลองใหม่เมื่อเหมาะสม
- Dialog และ form คืน focus ไปยังปุ่มต้นทางเมื่อปิด
- ทุก action สำคัญใช้งานด้วยคีย์บอร์ดได้ และข้อความผิดพลาดเชื่อมกับ input
- รองรับ Chrome ปัจจุบันที่ความกว้าง 360px และ 1280px

## 10. โครงสร้างไฟล์ที่คาดไว้

- `src/features/shop/domain/` — types และ validation
- `src/features/shop/data/` — catalog และ mock repository
- `src/features/shop/context/` — provider และ hooks
- `src/features/shop/components/` — tabs, filters, forms, dialogs และ calendar/list
- `src/app/(clinic)/departments/page.tsx` — composition ของหน้าแผนกและแพทย์
- `src/app/(clinic)/schedules/page.tsx` — composition ของหน้าปฏิทิน
- ไฟล์ทดสอบวางร่วมกับหน่วยที่ทดสอบหรือตามรูปแบบที่ Vitest ใน repo รองรับ

## 11. การทดสอบและการตรวจรับ

### Unit tests

- ตรวจเวลาเริ่ม/สิ้นสุด เวลาทำการ ช่วงพัก และรอบข้ามวัน
- ตรวจรอบทับ รวมกรณีขอบเวลาติดกัน
- ตรวจความจุ จำนวนจอง และการคำนวณ `full`
- ตรวจ hard delete กับ soft delete ตาม `hasHistory`
- ตรวจการอ้างอิงแผนกและสถานะ active

### Component/integration tests

- เพิ่มและแก้ไขแผนกหรือแพทย์แล้วตัวกรองกับรายการเปลี่ยนตาม
- รายการมีประวัติถูกปิดใช้งานและยังเปิดดูย้อนหลังได้
- สร้างรอบทับซ้อนถูกปฏิเสธพร้อมเหตุผล และข้อมูลเดิมไม่เปลี่ยน (AC06/SCN-03)
- ปฏิทินแสดงข้อมูลและสถานะถูกต้องเมื่อเปลี่ยนสัปดาห์หรือตัวกรอง (AC28)
- การจัดการแผนกและแพทย์รักษาความสัมพันธ์เดิม (AC29)
- loading, empty และ error แสดงครบ

### Quality gates

- `npm test`
- `npm run lint`
- `npx tsc --noEmit`
- `npm run build`
- ตรวจหน้า 360px และ 1280px รวม keyboard flow หลัก

## 12. เงื่อนไขสำเร็จ

- ผู้ใช้จัดการแผนก แพทย์ และรอบตรวจด้วย mock data ได้ครบตามขอบเขต
- validation สำคัญไม่ผูกกับ component และมีผลทดสอบรองรับ
- UI ไม่เรียก Supabase และไม่พึ่ง schema เดิม
- refresh แล้วกลับสู่ Catalog ตั้งต้นโดยไม่มีการเขียนข้อมูลภายนอก
- repository contract สามารถมี Supabase implementation เพิ่มภายหลังได้โดยไม่เปลี่ยน public behavior ของหน้า
