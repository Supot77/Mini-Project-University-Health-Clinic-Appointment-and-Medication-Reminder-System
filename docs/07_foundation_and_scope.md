# 07. ขอบเขตและสถานะโครงการ

ปรับปรุง 7 กันยายน 2569 (2026-09-07) — ฉบับ scope manual ขนาดเล็กตาม D22 ยังไม่ใช่หลักฐานว่าโค้ดหรือฐานข้อมูลทำครบแล้ว

## ขอบเขตที่ต้องคง

สมาชิก/รีเซ็ตรหัสผ่าน/โปรไฟล์/ค้นหาผู้ป่วย/เจ้าหน้าที่-แอดมินจัดบัญชี, แผนก/แพทย์/ปฏิทิน, นัด/คิว/ผลตรวจ/รายการยา, คลัง/จ่ายเต็ม, รายการเตือนแบบกรอกเอง, Broadcast และ Dashboard ตามบทบาท ดู [02](02_user_stories.md)

## สิ่งที่เปลี่ยนจากฐานก่อนประชุม

| ฐานเดิม | Scope ปัจจุบัน |
| --- | --- |
| มี worker, email และสถานะตามเวลา | ตัดออกทั้งหมด ให้ผู้ใช้กดบันทึกเอง |
| แบ่งจ่าย/กันยา/ยาค้าง | จ่ายเต็มครั้งเดียว หากไม่พอให้ปฏิเสธ |
| เจ้าหน้าที่/แอดมินตั้งเตือนและผู้ป่วยยืนยันเวลา | `staff_admin` กรอกรายการเตือน ผู้ป่วยบันทึกผลเอง |
| เลื่อนนัดและ no-show อัตโนมัติ | `staff_admin` จัดการนัดเดิมด้วยมือ ไม่มี workflow เลื่อนนัด |
| ตารางแพทย์สร้างหรือเปิด/ปิดอัตโนมัติ | `staff_admin` กรอกและปิด slot เอง |
| ข้อกำหนดมีข้อยกเว้นและเส้นตายย่อยจำนวนมาก | คง validation พื้นฐานและสิทธิ์เท่าที่จำเป็น |

ใช้ 3 บทบาทหนึ่งบทบาทต่อบัญชี: `patient`, `medical` (แพทย์/เภสัชกร) และ `staff_admin` (เจ้าหน้าที่/แอดมิน) ไม่ใช้ student เป็น role; เวลา Asia/Bangkok และข้อมูลเดโม 4 แผนก 17 บัญชีตาม [Catalog](superpowers/specs/2026-09-04-clinic-demo-data-design.md)

## สถานะ implementation

เอกสาร ER แบบแยกตารางและ migration 03 เป็นข้อเสนอจาก scope เดิม ให้ถือเป็นเอกสารอ้างอิงทางประวัติศาสตร์จนกว่าจะปรับ schema ให้ตรง scope ใหม่ runtime ยังใช้ mock และยังไม่ได้รัน migration/RLS/RPC กับฐานจริง

ไม่เพิ่ม walk-in, ลากวาง, กราฟขั้นสูง, Web Push, การจ่ายเงิน, หลายสาขาหรือเชื่อมโรงพยาบาลเป็นข้อบังคับ การคืนยาที่จ่ายแล้วและเรื่องที่ยังไม่ตอบดู [10](10_team_decisions.md)

## ความหมายของสถานะแต่ละแบบ

| สถานะ | หมายถึง | หลักฐานที่ใช้ยืนยัน |
| --- | --- | --- |
| ตกลงขอบเขต | ทีมยืนยันว่าต้องมีหรือไม่ต้องมี | ข้อความใน [10](10_team_decisions.md) |
| เตรียมแบบ | มี type, schema, mock หรือ contract รองรับ | ไฟล์ใน repository และการตรวจความสอดคล้อง |
| พัฒนาใน runtime | UI เรียก implementation ที่กำหนด | โค้ดและ test ที่รันได้ |
| ตรวจรับแล้ว | ผ่าน acceptance และ quality gates | ผลคำสั่งตรวจและหลักฐาน flow จริง |

การเพิ่มรายละเอียดในเอกสารทำให้การสื่อสารชัดขึ้นเท่านั้น ไม่เลื่อนสถานะจาก “เตรียมแบบ” เป็น “พัฒนาแล้ว” หรือ “ตรวจรับแล้ว” และไม่ทำให้ migration ถูก deploy โดยอัตโนมัติ

## เกณฑ์ตัดสินว่างานอยู่ใน scope

งานอยู่ใน scope เมื่ออธิบายได้จาก role contract, FR และ AC ปัจจุบัน และเชื่อมกับ flow manual ที่กำหนดไว้ งานที่ต้องมี worker, การรอเวลา, บริการภายนอก, ตารางใหม่ หรือกติกาย่อยที่ D22 ตัดออก ให้ถือว่านอก scope จนกว่าจะมีข้อสรุปทีมใหม่
