# 08. กติการะบบและเกณฑ์ตรวจรับ

ปรับปรุง 7 กันยายน 2569 (2026-09-07) — ฉบับ scope manual ขนาดเล็กตาม D22 ใน [10](10_team_decisions.md) ยังไม่ใช่หลักฐานว่าโค้ดหรือฐานข้อมูลทำครบแล้ว

## 1. หลักการ scope

- ระบบเป็น manual-first ไม่มี automation, worker, cron, retry, catch-up, email หรือ Web Push
- ระบบไม่เปลี่ยนสถานะจากเวลาเอง ทุกการอนุมัติ ปิด slot จบตรวจ จ่ายยา และบันทึกเตือนต้องมีผู้ใช้ที่มีสิทธิ์กดคำสั่ง
- ใช้ validation พื้นฐานเพื่อป้องกันข้อมูลผิดและข้อมูลซ้ำเท่านั้น ไม่เพิ่มกฎผ่อนผันหรือเส้นตายย่อย
- Runtime ใช้ Supabase จริงผ่าน database repository; automated unit/component tests ใช้ mock และไม่เรียกฐานจริงหรือบริการภายนอก

## 2. สิทธิ์

| บทบาท | งานหลัก | ขอบเขตจำกัด |
| --- | --- | --- |
| patient | โปรไฟล์ จองนัด ดูผลตรวจ/ยา รายการเตือน และ Dashboard ของตน | อ่านหรือแก้ข้อมูลของคนอื่นไม่ได้ และเข้า Dashboard ของ role อื่นไม่ได้ |
| medical | แพทย์ตรวจและบันทึกผล/รายการยา; เภสัชกรดูประวัติแพ้ยา จัดการยา และค้นหารายชื่อผู้ป่วย | แพทย์แก้เฉพาะนัดของตน; ไม่เปิด diagnosis ในส่วนงานคลังยา |
| staff_admin | จัดการ slot นัด วันลา บัญชี รายการเตือน สถิติรวม และ Broadcast ตามสิทธิ์ | Dashboard แสดงข้อมูลรวม ไม่เปิด diagnosis หรือผลตรวจ |

## 3. กติกาการทำงาน

- ทุก role มี guarded entry page/dashboard ของตน เมื่อข้อมูลหรือคำสั่งต่างกันต้องใช้ role-specific page/container/component; shared UI ใช้ร่วมกันได้เมื่อไม่มี permission logic
- UI guard และการซ่อนเมนูไม่ใช่ขอบเขตความปลอดภัยสุดท้าย ทุกคำสั่งต้องตรวจ session/role/ownership ใน service/repository และ Supabase RLS/RPC
- Production UI ห้ามมีตัวเลือกสลับ role เพื่อจำลองสิทธิ์ ผู้ทดสอบต้องเข้าสู่ระบบด้วยบัญชีของ role นั้น

- เจ้าหน้าที่/แอดมิน (`staff_admin`) หรือแพทย์เจ้าของงานกรอก slot เอง ตรวจไม่ให้เวลาทับกัน ไม่สามารถเพิ่มรอบตรวจของวันในอดีตได้ และปิด slot เองเมื่อจำเป็น
- ผู้ป่วย (`patient`) จอง slot ที่ว่างเป็น `pending`; `staff_admin` อนุมัติหรือปฏิเสธด้วยมือ
- `staff_admin` และ `medical` เปลี่ยนสถานะการตรวจด้วยมือ; `medical` จบตรวจได้เมื่อบันทึกผลตรวจแล้ว
- หากแพทย์ลา `staff_admin` ปิด slot และติดต่อจัดการนัดเดิมทีละรายการ ไม่มีการย้ายหรือยกเลิกอัตโนมัติ
- `medical` จ่ายเต็มตามจำนวนที่สั่งในครั้งเดียว หากยาไม่พอให้ปฏิเสธการจ่ายและบันทึกเหตุผล
- `staff_admin` สร้างรายการเตือนจากยาที่จ่ายเต็ม ผู้ป่วยกดบันทึกผลเองในเว็บ ไม่มีการคำนวณ `missed` หรือการเตือนซ้ำ
- `staff_admin` ส่ง Broadcast เมื่อกดส่งเท่านั้น

## 4. Acceptance Criteria

| รหัส | สถานการณ์ | ผลที่ต้องได้ |
| --- | --- | --- |
| AC01 | สมัครด้วยอีเมลนอกโดเมน | ระบบปฏิเสธและไม่สร้างบัญชี |
| AC02 | ผู้ใช้เปิดข้อมูลของบัญชีอื่น | ระบบปฏิเสธทั้ง UI และ service |
| AC03 | ผู้มีสิทธิ์สร้าง slot เวลาทับกัน ความจุไม่ถูกต้อง หรือเลือกวันในอดีต | ไม่บันทึกและแสดงข้อผิดพลาด |
| AC04 | Patient จอง slot เต็มหรือส่งคำขอซ้ำ | ไม่สร้างนัดซ้ำและจำนวนจองไม่เกินความจุ |
| AC05 | `staff_admin` อนุมัติ/ปฏิเสธนัด | สถานะเปลี่ยนตามคำสั่งและ role ที่ถูกต้อง |
| AC06 | `medical` จบตรวจโดยไม่มีผลตรวจ หรือแก้นัดของแพทย์อื่น | ระบบปฏิเสธและข้อมูลเดิมไม่เปลี่ยน |
| AC07 | `staff_admin` จัดการนัดเมื่อแพทย์ลา | เปลี่ยนเฉพาะรายการที่เลือก ไม่มี auto-cancel หรือ auto-reschedule |
| AC08 | `medical` จ่ายยาเมื่อ stock ไม่พอ | ปฏิเสธการจ่าย ไม่ตัด stock และแสดงเหตุผล |
| AC09 | `medical` จ่ายเต็มสำเร็จ | ตัด stock ตามจำนวนจริงและบันทึกผู้ทำกับเวลา |
| AC10 | `staff_admin` สร้างเตือนจากยาที่ยังไม่จ่ายเต็ม | ระบบปฏิเสธการสร้าง |
| AC11 | Patient บันทึกผลเตือนของบัญชีอื่น | ระบบปฏิเสธ |
| AC12 | `staff_admin` ส่ง Broadcast | ข้อความถูกสร้างเมื่อกดส่ง และไม่มีการส่งซ้ำตามเวลา |
| AC13 | คำสั่งใด validation ไม่ผ่าน | state เดิมไม่เปลี่ยน |
| AC14 | เปิดหน้าหลังเวลาผ่านไป | ระบบไม่เปลี่ยนสถานะนัด ยา หรือเตือนเอง |
| AC15 | ระบบทดสอบ | ไม่เรียก network, email provider, worker หรือฐานข้อมูลจริง |
| AC16 | Runtime อ่านหรือเขียนข้อมูลหลัก | ใช้ Supabase database repository และบังคับสิทธิ์ด้วย session + RLS/RPC ไม่มี mock fallback แบบเงียบ |
| AC17 | ผู้ใช้เปิด entry page หรือ flow ของ role อื่น | route/layout guard ปฏิเสธหรือ redirect และ query ฐานข้อมูลไม่คืนข้อมูลเกินสิทธิ์ |
| AC18 | Flow ที่ role มีข้อมูลหรือคำสั่งต่างกัน | render role-specific page/container โดยไม่มี production role switcher และยังใช้ shared presentational component ได้ |

## 5. เส้นทางสาธิตขั้นต่ำ

1. ผู้ป่วยสมัครและเข้าสู่ระบบ
2. `staff_admin` สร้าง slot และผู้ป่วยจอง
3. `staff_admin` อนุมัตินัด และ `medical` บันทึกผลตรวจ
4. `medical` จ่ายยาเต็ม และ `staff_admin` กรอกรายการเตือน
5. ผู้ป่วยเปิดรายการของตนและกดบันทึกผลด้วยมือ
6. `staff_admin` ส่ง Broadcast ด้วยมือ

ไม่มี SCN สำหรับเลื่อนนัดอัตโนมัติ แบ่งจ่าย/กันยา ยาค้าง email worker missed หรือการเตือนซ้ำ

## 6. เกณฑ์ส่งมอบ

ต้องตรวจ lint, typecheck, test และ build ตามคำสั่งใน README ตรวจ flow หลักด้วย Chrome ที่ 360px และ 1280px รวม keyboard, loading, empty และ error และตรวจ database integration/RLS กับฐาน development หรือ staging ที่ระบุชัดก่อนอ้างว่าเชื่อมฐานจริงผ่าน รายงานผลจริง ไม่ถือว่าเอกสารเป็นหลักฐานว่าระบบผ่านการตรวจรับแล้ว

## วิธีใช้ Acceptance Criteria

แต่ละ AC ต้องตรวจทั้งผลที่ผู้ใช้เห็นและ state หลังคำสั่ง: ระบุบัญชีหรือ role ที่ใช้, ข้อมูลตั้งต้น, คำสั่งที่ทำ, ผลลัพธ์ที่แสดง และข้อมูลที่ยังคงเดิมเมื่อคำสั่งถูกปฏิเสธ กรณีสำเร็จต้องตรวจความสัมพันธ์ของข้อมูลที่เปลี่ยนด้วย เช่น จำนวนจอง, ผลตรวจ, stock หรือ notification ที่เกิดขึ้น

AC01–AC05 ตรวจสมาชิก ตาราง และการตัดสินนัด; AC06–AC09 ตรวจสิทธิ์การตรวจและการจ่ายยา; AC10–AC12 ตรวจรายการเตือนและ Broadcast; AC13–AC15 ตรวจความสมบูรณ์ของ state, การไม่เปลี่ยนตามเวลา และการแยก test จากบริการภายนอก; AC16–AC18 ตรวจ database runtime, RLS และ UI แยกตาม role

## หลักฐานขั้นต่ำของกรณีไม่ผ่าน

เมื่อ validation หรือ permission ไม่ผ่าน ต้องบันทึก error ที่ระบุสาเหตุได้ และยืนยันค่าที่สำคัญก่อนกับหลังเท่ากัน เช่น สถานะนัด, จำนวนจอง, stock, รายการเตือน หรือกล่องข้อความ กรณีเปิดหน้าหลังเวลาผ่านไปต้องยืนยันด้วยว่าสถานะยังเปลี่ยนได้เฉพาะจากคำสั่งที่มีสิทธิ์
